# Architecture and decisions

Why this project is built the way it is. Each decision records what was actually
verified, so a future reader can tell evidence from assumption.

---

## Decision 1: Objective YAML is the single source of truth

`content/objectives/*.yaml` holds every exam objective, quoted from the official
guides, under a **stable ID** (`ASSOC-S2-O3`, `PRO-S1-O7`).

Everything else derives from it: the markdown maps in `docs/exam-guides/` are
generated by `tools/render_objectives.py`, questions link to objectives by ID,
and assignments declare which IDs they exercise. `--check` fails CI if a
generated doc drifts from its source.

**IDs are a contract and must never be renumbered.** If Databricks restructures a
guide, add new IDs and mark old ones removed — renumbering would silently
re-point every question and lesson that references them.

---

## Decision 2: Free Edition is the baseline, and the gaps are labelled

Everything on the required path must run on a personal Free Edition workspace, so
any learner can reproduce the whole thing without a paid account.

Free Edition is serverless-only, which means a handful of objectives — the ones
*about* classic compute — genuinely cannot be practised on it. Rather than quietly
downgrade those to reading material, each objective carries an honest tag:

| Tag | Meaning |
| --- | --- |
| *(absent)* | Fully practisable on Free Edition |
| `free_edition_lab: partial` | Concept reachable, some of the surface isn't |
| `free_edition_lab: theory_only` | Not practisable on Free Edition at all |
| `optional_classic_lab: true` | A classic-compute lab exists; needs Premium/trial |
| `verify_in_workspace: true` | Feasibility genuinely unknown — confirm, don't guess |

The `verify_in_workspace` flag exists because guessing is the failure mode here.
It marks objectives where the docs were ambiguous and only a live workspace can
settle it.

See [free-edition-constraints.md](free-edition-constraints.md) for the measured
platform limits, and [optional-classic-track.md](optional-classic-track.md) for
the paid-tier track.

## Decision 3: AppKit on Free Edition — verified, not assumed

**Status: ✅ verified 2026-09-09 against `REDACTED.cloud.databricks.com`.**

### The risk

Databricks Apps builds install dependencies from `registry.npmjs.org` (plus
`pypi.org`, `files.pythonhosted.org`, `*.databricksapps.com`). Free Edition
restricts outbound egress to a trusted-domain list it **cannot customise** —
network policies are an Enterprise-tier feature. If npm were not on that list,
every AppKit plan would have been dead on arrival.

Published documentation did not settle it: the Free Edition limitations page says
only "a limited set of trusted domains" without naming them.

### The spike

A throwaway app was scaffolded with no optional plugins (`server` is the only
plugin `requiredByTemplate`, and it needs no resources — the smallest possible
test) and deployed:

```
✓ Downloading source code
✓ Installing packages...      ← the actual question
✓ Building app...
✓ App started successfully
```

`app_status: RUNNING`, reachable at a `*.aws.databricksapps.com` URL. The app was
then destroyed to return the quota to 3/3.

### Conclusion

**AppKit (TypeScript/React) is viable on Free Edition.** Remote npm install and
remote build both work. The fallbacks that were on standby — vendoring
`node_modules`, a locally-built SPA served by FastAPI, or an externally-hosted
study UI — are **not needed** and should not be built.

### What still constrains the app

- **3 apps per account.** Budget them; delete throwaways.
- **Apps auto-stop 24h** after being started, updated or redeployed. This is a
  study tool you spin up, *not* an always-on site for other people. A one-command
  redeploy is documented, and a static export keeps studying unblocked when the
  app is down.
- App compute reports as size `MEDIUM`.

## Decision 4: Lakebase for user state, git for content

The app scaffolds with `--features lakebase` and **no** `analytics` feature.

- **Content** (objectives, lessons, questions) lives in git and ships to the app
  as build-time JSON. It's reviewable in pull requests, diffable, and correct by
  validation — none of which a database gives us.
- **User state** (attempts, spaced-repetition schedule, assignment results) goes
  in Lakebase Postgres. It must survive the 24h app auto-stop, which rules out
  browser storage, and it's per-user mutable, which is a poor fit for a SQL
  warehouse.

Free Edition allows exactly **one Lakebase project**, scale-to-zero. This app
uses it.

Consequence: the app does not read Unity Catalog analytics tables, so the
analytics plugin, `config/queries/`, and `useAnalyticsQuery` are all deliberately
absent. Adding them later means re-running the data-access decision.

## Decision 5: Paired datasets — the anti-transplant property

Every lesson teaches on a `teach` dataset; every assignment is set on a
structurally different `assess` dataset. The goal is that **assignment code cannot
be assembled by pasting from the lesson**.

Cosmetic differences don't achieve this — renamed columns fall to find-and-replace.
So each pair must differ in at least two of: shape (flat vs nested), types (ISO
strings vs epoch millis), edge cases (the `assess` set carries a hazard the
`teach` set lacks), or grain.

This is a testable property, not an aspiration: for each assignment, the lesson's
own solution is pasted in and the suite **must fail** on the assess-only hazards.
If it passes, the pairing is broken and gets redesigned.

## Decision 6: Two grading tiers, and only one of them is authoritative

**Tier 1 — unit tests. Authoritative.** Each assignment declares an output
contract; a pytest suite asserts schema, row counts, known-answer probes and
edge-case handling. Deterministic and offline.

This tier is doing double duty: it's built from `assertDataFrameEqual`,
`assertSchemaEqual` and `DataFrame.transform`, which is *precisely* what
`PRO-S1-O11` examines. The grading harness is itself a worked example.

**Tier 2 — AI review. Advisory, bring your own model.** Unit tests can't tell
whether the learner used the intended technique — a loop over `read.json` may pass
every assertion while entirely missing Auto Loader. An LLM can judge that, and can
grade prose justifications.

Rules that keep this honest:

- The learner attaches their own model; the repo ships **no credentials**.
  Databricks Foundation Model APIs on their own workspace is the recommended
  option — no extra signup.
- Output is structured JSON, so it renders as feedback rather than a wall of prose.
- **An AI verdict never overrides a unit test.** LLM graders are
  non-deterministic; where the two disagree, both are shown and the test wins.
- Every assignment must be fully gradeable by tier 1 alone, so attaching no model
  still yields a real pass/fail.

## Decision 7: Section-level assignments

One graded assignment per **section** (17 total), not per objective (78).

Per-objective would be unmaintainable and repetitive. Section-level is also better
pedagogy: it forces objectives to be *combined*, which is closer to both the exam
and real work. High-weight sections may earn a second assignment.

Each assignment declares the `objective_ids` it exercises, so coverage stays
measurable and the validator can flag any objective nothing touches.

---

## Decision 8: No exam content, ever

The repo carries the 14 retired sample questions Databricks publishes in the guides
(attributed, `provenance: official-sample`) and otherwise **original** questions.

For questions inspired by third-party courses: only the *concept under test* is
taken, mapped to an objective ID. The wording, scenario, numbers and options are
discarded and written fresh (`provenance: concept-inspired`). Lightly reworded
questions are still derivative works — "changed a bit" does not clear copyright.

Real exam content is under NDA and never enters this repo, including in commit
messages and issues.
