# Data Modeling — 6%

A small section with two ideas the exam returns to: **state the grain before you
write code**, and **a natural key identifies an entity only while nothing about
it changes**. The rest is layout, where liquid clustering replaces the decisions
partitioning forced you to make once.

> **Names:** Lakeflow Spark Declarative Pipelines (Delta Live Tables, DLT), `AUTO CDC` (`APPLY CHANGES`), automatic liquid clustering `CLUSTER BY AUTO` (not auto optimize: `optimizeWrite` and `autoCompact` only size files), Z-order (`ZORDER BY`, still current, but not a liquid clustering mode).

## What the exam asks

- A revenue-by-segment report attributes January's sales to the segment a customer moved into in June — the fact joined the current dimension row instead of the version in effect (`PRO-S10-O4`)
- A fact joined to a Type 2 dimension comes back with more rows than it went in with — overlapping validity windows, or `<=` on the end bound (`PRO-S10-O4`)
- Surrogate keys change every time the dimension is rebuilt, and published facts point at the wrong customers — the key must be deterministic, not `monotonically_increasing_id()` (`PRO-S10-O1`)
- A team does not yet know how analysts will filter a new fact table — `CLUSTER BY AUTO` on a managed table with predictive optimization (`PRO-S10-O2`)
- Queries filter on a fifth column and `OPTIMIZE ... ZORDER BY` fails on the table — liquid clustering caps keys at four and refuses `ZORDER` (`PRO-S10-O3`)
- A 300 GB table is partitioned by day and full of small files — under 1 TB, don't partition; convert to liquid clustering (`PRO-S10-O3`)

## Defaults and limits

| Setting | Default or limit | Note |
|---|---|---|
| Clustering keys | at most **4** | a fifth fails with `DELTA_CLUSTER_BY_INVALID_NUM_COLUMNS` |
| Statistics columns | first **32** columns | `delta.dataSkippingNumIndexedCols`; a clustering key must have statistics |
| `CLUSTER BY AUTO` | managed Unity Catalog tables, predictive optimization on, DBR 15.4 LTS+ | external tables cannot use it |
| Clustering on write | from **64 MB** (1 key) to **1 GB** (4 keys) per transaction on managed tables | 256 MB to 4 GB on other Delta tables; smaller writes wait for `OPTIMIZE` |
| `OPTIMIZE` on a clustered table | incremental, new data only | `OPTIMIZE ... FULL` (DBR 16.4 LTS+) reclusters everything |
| Partition size | at least **1 GB** per partition | |
| Table size to partition | don't partition under **1 TB** | 1 to 100 TB: liquid clustering instead |
| Identity column | `BIGINT` only, `START WITH 1`, `INCREMENT BY 1` | step can be negative, not 0; values unique, not contiguous |
| Constraint optimisation | `NORELY` | `RELY` lets the optimiser use the key; needs Photon |
| Primary key columns | made `NOT NULL` implicitly | PK, FK and `UNIQUE` are never enforced |
| `delta.columnMapping.mode` | `none` | `name` (any time) or `id` (create time only); protocol reader 2, writer 5 |
| SCD2 open end | `valid_to = 9999-12-31` | a convention, not a setting; `NULL` works but makes the join harder |

## Scalable models on Delta — `PRO-S10-O1`

Delta gives a model ACID writes, schema enforcement, time travel and concurrent
readers, so the modelling decisions are about **grain and keys**, not storage
mechanics. State the fact's grain in words first: "one row per sale" is a grain;
"sales data" is not. Design so a rebuild is deterministic: a surrogate key derived
from a hash of the natural key and validity start survives a rebuild;
`monotonically_increasing_id()` does not, and every fact already published then
points somewhere else. Keep bronze append-only and raw, silver conformed, gold
modelled; the model is the gold layer.

### Identity columns

An identity column is the other way to produce a surrogate key: Delta assigns
it on insert, including inserts from a `MERGE`.

```sql
CREATE TABLE gold.dim_customer (
  customer_sk BIGINT GENERATED ALWAYS AS IDENTITY (START WITH 1 INCREMENT BY 1),
  customer_id STRING  NOT NULL,          -- natural key
  segment     STRING,
  valid_from  DATE    NOT NULL,
  valid_to    DATE    NOT NULL,
  is_current  BOOLEAN NOT NULL
);

-- GENERATED BY DEFAULT accepts an explicit value; ALWAYS refuses one
-- after explicit values, realign the high-water mark:
ALTER TABLE gold.dim_customer ALTER COLUMN customer_sk SYNC IDENTITY;
```

What the exam probes: identity columns are `BIGINT` only; values are unique and
move in the step direction but **are not contiguous**; declaring one **disables
concurrent transactions** on the table; you cannot partition by it, cannot add or
change one with `ALTER TABLE`, and cannot update a row's value. Because the value
depends on insert order, a full rebuild can hand the same customer a different
key, so identity suits a dimension that is only ever appended to and merged into,
not one rebuilt from scratch. A hash key (`xxhash64(customer_id, valid_from)`) is
the rebuild-safe choice.

> **Measured on Free Edition:** an explicit value for a `GENERATED ALWAYS` column
> fails with `DELTA_IDENTITY_COLUMNS_EXPLICIT_INSERT_NOT_SUPPORTED`. With
> `GENERATED BY DEFAULT`, inserting 99 explicitly and then one generated row gave
> the generated row 1, not 100. An SCD2 `MERGE` filled the identity for both
> inserted rows (3 and 4), in an order unrelated to the source.

### Informational keys and `RELY`

Primary and foreign keys document the model for BI tools and the optimiser.
Databricks **does not enforce** them; only `NOT NULL` and `CHECK` are enforced.

```sql
ALTER TABLE gold.dim_customer
  ADD CONSTRAINT dim_customer_pk PRIMARY KEY (customer_sk) RELY;   -- default NORELY

CREATE TABLE gold.fact_sales (
  sale_id     BIGINT NOT NULL,
  customer_sk BIGINT,
  amount      DECIMAL(10,2),
  sold_on     DATE,
  CONSTRAINT fact_sales_pk PRIMARY KEY (sale_id),
  CONSTRAINT fact_sales_customer_fk FOREIGN KEY (customer_sk)
    REFERENCES gold.dim_customer   -- parent columns default to its PK
) CLUSTER BY (sold_on, customer_sk);
```

`RELY` tells the optimiser it may trust the key, for example to drop a `LEFT JOIN`
to a dimension whose columns the query never reads. That is safe only if the data
really is unique: a `RELY` key over duplicates returns wrong answers, not an
error. Keep a uniqueness test in the pipeline that loads the table.

> **Measured on Free Edition:** a duplicate `sale_id` and an orphan `customer_sk`
> both inserted without complaint. A `PRIMARY KEY` on a nullable column was
> accepted and a later `NULL` insert failed with `DELTA_NOT_NULL_CONSTRAINT_VIOLATED`.
> `SELECT f.sale_id FROM f LEFT JOIN d ...` kept the join in the plan when `d`
> had no constraint or a `NORELY` key, and scanned only `f` when the key was `RELY`.

### Column mapping

A model changes; column mapping lets you rename or drop a column as a metadata
change instead of rewriting the files.

```sql
ALTER TABLE gold.dim_customer
  SET TBLPROPERTIES ('delta.columnMapping.mode' = 'name');   -- default 'none'
ALTER TABLE gold.dim_customer RENAME COLUMN segment TO customer_segment;
ALTER TABLE gold.dim_customer DROP COLUMN legacy_flag;
```

`name` can be set on an existing table; `id` only at create time. It upgrades
the protocol (reader 2, writer 5), and turning it off rewrites every data file.
Renames and drops are non-additive schema changes, so a stream reading the table
needs `schemaTrackingLocation` or it stops.

> **Measured on Free Edition:** without column mapping, `RENAME COLUMN` and
> `DROP COLUMN` fail with `DELTA_UNSUPPORTED_RENAME_COLUMN.ENABLE_COLUMN_MAPPING`
> and `DELTA_UNSUPPORTED_DROP_COLUMN.ENABLE_COLUMN_MAPPING`; after setting `name`
> both succeed. A new managed table did not have column mapping on by default.

## Dimensional models — `PRO-S10-O4`

| | Holds | Grain | Grows |
|---|---|---|---|
| **Fact** | measurements and foreign keys | one row per event | continuously |
| **Dimension** | descriptive attributes | one row per entity (or version) | slowly |

| | |
|---|---|
| **Natural key** | the business identifier, `customer_id` |
| **Surrogate key** | a model-generated key identifying **one version** of a row |

A **star** keeps dimension attributes denormalised in one table: fewer joins,
some redundancy. A **snowflake** normalises them into sub-dimensions: less
redundancy, more joins. Star is the default for analytics; storage is cheap and
a four-join "revenue by region" is not. Databricks' own guidance says star and
snowflake both perform well and advises against third normal form for analytics.

### Fact types and measures

These are the standard Kimball definitions; the exam uses the words without
defining them.

| Fact type | One row per | Example | Updated? |
|---|---|---|---|
| **Transaction** | event | one sale line | never, insert only |
| **Periodic snapshot** | entity per period | account balance at each month end | never, a new row each period |
| **Accumulating snapshot** | process instance | an order with ordered, shipped, delivered dates | yes, as milestones land |
| **Factless** | event with no measure | a student attending a class | insert only; you count rows |

| Measure | Sums across | Example |
|---|---|---|
| **Additive** | every dimension | `amount`, `quantity` |
| **Semi-additive** | some dimensions, not time | a balance: sum across accounts, not across months (take the last, or average) |
| **Non-additive** | none | a ratio or unit price: sum the numerator and denominator, then divide |

Storing `margin_pct` on the fact and summing it is the non-additive trap; store
`revenue` and `cost` and compute the percentage after aggregation.

### Slowly changing dimensions

| Type | On change | History | Fact joins on |
|---|---|---|---|
| **SCD 1** | overwrite the attribute in place | none | natural key (or a stable surrogate) |
| **SCD 2** | close the current row, insert a new version | full | surrogate key, or natural key plus date range |
| **SCD 3** | move the old value to a `previous_` column | one prior value | natural key |

```sql
-- SCD 1: plain upsert
MERGE INTO gold.dim_customer t USING updates s ON t.customer_id = s.customer_id
WHEN MATCHED THEN UPDATE SET segment = s.segment
WHEN NOT MATCHED THEN INSERT (customer_id, segment) VALUES (s.customer_id, s.segment);

-- SCD 3: keep one previous value
MERGE INTO gold.dim_customer_scd3 t USING updates s ON t.customer_id = s.customer_id
WHEN MATCHED AND NOT (t.segment <=> s.segment) THEN
  UPDATE SET previous_segment = t.segment, segment = s.segment
WHEN NOT MATCHED THEN
  INSERT (customer_id, segment, previous_segment) VALUES (s.customer_id, s.segment, NULL);
```

**When the dimension changes, the natural key stops identifying a row.** A Type
2 dimension keeps one row per *version* with `valid_from` (inclusive) and
`valid_to` (exclusive), a surrogate key per version, and `is_current`. The fact
joins to the version in effect on its own date:

```sql
ON  f.customer_id = d.customer_id
AND f.ordered_on >= d.valid_from
AND f.ordered_on <  d.valid_to
```

The bounds are asymmetric on purpose: an order on a changeover date matches
exactly one version. **A dimension join must not change the fact's row count.**
More rows means the windows overlap; fewer means a gap. And the wrong answer here
is not an error: joining on `customer_id` to the current version returns every
order, no nulls, and a revenue-by-segment breakdown that quietly attributes
January's revenue to the segment the customer moved into in June.

A strict `>` on the start bound is the quieter mistake. Orders on a customer's
first day match nothing, and if the end bound is `<=`, changeover orders attach
to the *outgoing* version: the count drops by the first-day orders only, and the
rows that moved still look matched. If the open end is stored as `NULL`, a plain
`< d.valid_to` never matches the current row; use
`coalesce(d.valid_to, DATE'9999-12-31')` or `d.valid_to IS NULL OR ...`.

![Move an order onto a changeover date and switch the predicate](visual:scd2-boundary-join?h=900)

> **Measured on Free Edition:** with C1 moving SMB→MID on 2026-04-01 and
> MID→ENT on 2026-07-01, and five orders including C1's first day and both
> changeover dates, the inner join returned 5 rows with `>= / <`, 7 with
> `>= / <=`, 2 with `> / <` and 4 with `> / <=`. With the current row's
> `valid_to` set to `NULL`, `< d.valid_to` dropped both orders from 2026-07-01 on;
> the `coalesce` form brought them back.

### SCD2 MERGE, line by line

One `MERGE` can only touch each target row once, but a changed customer needs
two actions: close the old row and insert a new one. The standard fix is to send
each changed customer through the source **twice**.

```sql
MERGE INTO gold.dim_customer AS t
USING (
  SELECT u.customer_id AS merge_key, u.*          -- (1) every update, keyed
  FROM updates u
  UNION ALL
  SELECT NULL AS merge_key, u.*                   -- (2) changed rows again, unkeyed
  FROM updates u
  JOIN gold.dim_customer d
    ON  u.customer_id = d.customer_id
    AND d.is_current
    AND NOT (u.segment <=> d.segment)
) AS s
ON  t.customer_id = s.merge_key                   -- (3) a NULL key never matches
AND t.is_current
WHEN MATCHED AND NOT (t.segment <=> s.segment) THEN
  UPDATE SET is_current = false,                  -- (4) close the old version
             valid_to   = s.effective_date
WHEN NOT MATCHED THEN
  INSERT (customer_id, segment, valid_from, valid_to, is_current)
  VALUES (s.customer_id, s.segment, s.effective_date, DATE'9999-12-31', true);  -- (5)
```

1. Branch (1) carries every update with its real key. For a **changed** customer
   it matches the current row and closes it at (4). For an **unchanged** one it
   matches, fails the `AND NOT (...)` condition, and does nothing. For a **new**
   one it matches nothing and is inserted at (5).
2. Branch (2) repeats only the changed customers, with `merge_key` set to `NULL`.
3. `t.customer_id = NULL` is never true, so those rows always fall to
   `WHEN NOT MATCHED` and become the new current version at (5).
4. The old row's `valid_to` is the new row's `valid_from`: the same date on both,
   which is exactly what the half-open `<` join needs.
5. `<=>` is null-safe equality. With plain `<>`, a change from `NULL` to a value
   is not detected, because `NULL <> 'ENT'` is `NULL`, not true.

Run it twice with the same input and nothing changes: after the first run every
customer's current row already carries the new value, so branch (2) is empty and
branch (1) matches without changing anything. Deduplicate `updates` to one row
per `customer_id` first; two source rows matching one target row fail the
`MERGE`. In a declarative pipeline, `AUTO CDC ... STORED AS SCD TYPE 2` writes
this logic for you, including late-arriving changes.

> **Measured on Free Edition:** with C1 changing SMB→ENT, C2 unchanged and C4
> new, the `MERGE` reported 1 updated and 2 inserted rows
> (`numSourceRows` 4: three keyed plus one unkeyed). A second identical run
> affected 0 rows. Orders on 2026-03-01 and on the changeover date 2026-06-01
> joined to 3 rows with `<` and 4 with `<=`; joining to `is_current` instead
> put all 220.00 of revenue under ENT, against SMB 100.00 / ENT 120.00 with the
> date-range join.

### Grain violations that pass tests

The usual tests are "the key is not null" and "every fact has a matching
dimension row". Each violation below passes both.

| Violation | Not-null test | Orphan test | What catches it |
|---|---|---|---|
| Two overlapping current versions of one customer | passes | passes | row count before and after the join; one `is_current` per natural key |
| `<=` on the end bound | passes | passes | row count before and after the join |
| Join to `is_current` instead of the date range | passes | passes | nothing structural; compare history-sensitive totals |
| Order headers and order lines in one fact | passes | passes | uniqueness on the stated grain columns |
| A reload appends the batch twice under a `PRIMARY KEY` | passes | passes | an explicit uniqueness test; the PK is not enforced |

```sql
-- the grain is unique
SELECT sale_id, count(*) FROM gold.fact_sales GROUP BY sale_id HAVING count(*) > 1;
-- one current version per customer
SELECT customer_id FROM gold.dim_customer WHERE is_current
GROUP BY customer_id HAVING count(*) > 1;
-- no overlapping windows
SELECT a.customer_id FROM gold.dim_customer a JOIN gold.dim_customer b
  ON  a.customer_id = b.customer_id AND a.customer_sk < b.customer_sk
  AND a.valid_from < b.valid_to AND b.valid_from < a.valid_to;
```

> **Measured on Free Edition:** after appending an overlapping current row for
> C2, null keys were 0 and orphan facts were 0, yet 3 fact rows joined to 4. The
> one-current-version and overlap queries above each returned C2.

## Layout with liquid clustering — `PRO-S10-O2`

`CLUSTER BY (col, ...)` records the keys on the table. There are no directories:
the engine groups rows into files by those columns and file-level statistics let
it skip the files that cannot match. Cluster a fact on what it is filtered by,
usually the date and the highest-traffic dimension key. `CLUSTER BY AUTO` lets
Databricks choose and revise keys from the query history, the honest default
when you do not yet know the access pattern.

```sql
CREATE TABLE gold.fact_sales (...) CLUSTER BY (sold_on, customer_sk);  -- up to 4 keys
ALTER TABLE gold.fact_sales CLUSTER BY (region, sold_on);   -- new keys; old files stay
ALTER TABLE gold.fact_sales CLUSTER BY AUTO;                -- Databricks picks keys
ALTER TABLE gold.fact_sales CLUSTER BY NONE;                -- stop clustering; no rewrite
OPTIMIZE gold.fact_sales;           -- incremental: clusters what is not yet clustered
OPTIMIZE gold.fact_sales FULL;      -- recluster everything, e.g. after changing keys
DESCRIBE DETAIL gold.fact_sales;    -- clusteringColumns, clusterByAuto
```

`CLUSTER BY AUTO` needs three things: a **Unity Catalog managed** table,
**predictive optimization** enabled (it does the key selection and the
`OPTIMIZE` runs), and DBR 15.4 LTS or later. An external table cannot use it,
which makes "the table is external" the usual reason an `AUTO` answer is wrong.

Clustering keys must be columns with statistics, which by default means the
first 32 columns. Put candidate keys early in the schema, or raise
`delta.dataSkippingNumIndexedCols`.

On a clustered table, `OPTIMIZE` clusters **new data only**, so runs stay cheap
as the table grows. `ZORDER` is not incremental: it re-sorts everything it
touches every time. Writes cluster on the way in only above a size threshold
(64 MB for one key on a managed table, rising to 1 GB for four), so small
appends land unclustered until `OPTIMIZE` or predictive optimization runs.
Changing keys does not rewrite existing data; `OPTIMIZE ... FULL` does. A table
is partitioned or clustered, never both.

> **Measured on Free Edition:** a fifth key fails with
> `DELTA_CLUSTER_BY_INVALID_NUM_COLUMNS`; clustering on the 33rd column of a
> 33-column table fails with `DELTA_CLUSTERING_COLUMN_MISSING_STATS` and on the
> 32nd succeeds. After `CLUSTER BY AUTO`, `DESCRIBE DETAIL` showed
> `clusterByAuto = true` with the previous keys still in `clusteringColumns`;
> `CLUSTER BY NONE` set both back to `false` and `[]`.

## Clustering over partitioning and ZORDER — `PRO-S10-O3`

| | Partitioning | ZORDER | Liquid clustering |
|---|---|---|---|
| Set at | create time, fixed | each `OPTIMIZE` | any time, `ALTER TABLE` |
| Physical form | directories | sort order within files | file grouping |
| Incremental | n/a | **no** | **yes**, new data only |
| Skew | one big partition | tolerated | spread across files |
| Small files | the classic cause | does not fix the layout | targets file size |
| Change your mind | rewrite the table | free, but pay the sort | metadata change |

```sql
CREATE TABLE silver.events (event_date DATE, user_id BIGINT, ...)
PARTITIONED BY (event_date);
OPTIMIZE silver.events WHERE event_date >= '2026-10-01'   -- WHERE: partition columns only
ZORDER BY (user_id);                                       -- ZORDER: data columns only

-- convert in place (DBR 18.1+); ALTER TABLE ... CLUSTER BY alone is refused
ALTER TABLE silver.events REPLACE PARTITIONED BY WITH CLUSTER BY (event_date, user_id);

-- overwrite one slice
INSERT INTO silver.events REPLACE WHERE event_date = '2026-10-19'
SELECT * FROM staging.events_2026_10_19;
```

Databricks' sizing rule: don't partition a table under 1 TB; between 1 and
100 TB use liquid clustering instead; if you do partition, each partition
should hold at least 1 GB. A hot key becomes a straggler directory; a
fine-grained key becomes thousands of tiny files. Clustering keys
can be changed later; a partition column cannot without rewriting the table, and
on a fact table that grows for years that difference compounds.

Partitioning still wins when partitions are large, when you need to **drop or
overwrite whole slices cheaply** (`REPLACE WHERE` on a partition column drops the
old slice's files by metadata alone and writes only the new slice; on a clustered
table the same statement has to read files to find the matching rows and rewrite
the survivors), or when an external consumer
depends on the directory layout. "Always cluster" is not the lesson; "cluster
unless you can name the reason to partition" is.

`REPLACE WHERE` is also a guard: every row written must satisfy the predicate,
so a mislabelled batch fails rather than landing in the wrong slice.

> **Measured on Free Edition:** on 30,000 rows over three dates, `REPLACE WHERE`
> one date on the table partitioned by date removed 1 file, copied 0 rows and
> added 0 deletion vectors. On the same data clustered by date (the initial
> write was below the clustering threshold, so all dates shared one file) it
> copied 20,000 rows and added 1 deletion vector. Writing a row outside the
> predicate failed with `DELTA_REPLACE_WHERE_MISMATCH`. `ZORDER BY` a partition
> column fails with `DELTA_ZORDERING_ON_PARTITION_COLUMN`; `ZORDER BY` on a
> clustered table fails with `DELTA_CLUSTERING_WITH_ZORDER_BY`; `ALTER TABLE ...
> CLUSTER BY` on a partitioned table fails with
> `DELTA_ALTER_TABLE_CLUSTER_BY_ON_PARTITIONED_TABLE_NOT_ALLOWED`, and
> `REPLACE PARTITIONED BY WITH CLUSTER BY` converted it.
